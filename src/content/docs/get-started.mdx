Ndigo targets **Node.js ≥ 24** and **pnpm ≥ 12**. Make sure both are installed
before continuing.

<Steps>

1. **Scaffold a new app**

   ```bash
   pnpm create ndigo-app my-app
   cd my-app
   ```

   The scaffold ships a minimal application with routing, a view, and a
   development server configured. See the
   [Scaffolding reference](/reference/scaffolding/) for options.

2. **Install dependencies**

   ```bash
   pnpm install
   ```

3. **Start the dev server**

   ```bash
   pnpm dev
   ```

   Open the printed URL in your browser. You should see the starter page.

4. **Add your first route**

   Open `src/app.ts` (or the controller file the scaffold created) and add a
   route:

   ```ts
   import { routeMapping, ModelAndView } from '@ndigo/dispatcher';

   @routeMapping('/hello/:name')
   handleHello(name: string) {
       return new ModelAndView('hello', { name });
   }
   ```

5. **Create the view**

   Add a view component that renders the model:

   ```ts
   import { WebComponentView } from '@ndigo/view-webcomponent';

   export class HelloView extends WebComponentView {
       constructor() { super('hello-view'); }
   }
   ```

   Register it in your application configuration and you're done.

   The handler returned a **name**, so the preset's resolver chain picks the
   view. Where that view lands is a separate choice: the browser preset renders
   into `#app` by default, while named regions, page layouts, and other
   destinations are wired with ordered view targeters — see
   [Views, Targets & Content Negotiation](/guides/views-and-content-negotiation/#7-view-targets-and-view-targeting).

</Steps>

## Next steps

- Read [Core Concepts & Mental Model](/guides/core-concepts/) for the five
  nouns and how a request becomes a rendered view.
- Choose your runtime:
  - [Building a Node API](/guides/building-a-node-api/) for the server
    workflow.
  - [Building a Browser App](/guides/building-a-browser-app/) for the browser
    twin.
- Choose how views are placed: hand the dispatcher a view instance (local, one
  screen) or return a name and let a targeter choose the region (centralized
  layouts) — the basics are in
  [Views & Content Negotiation §7](/guides/views-and-content-negotiation/#7-view-targets-and-view-targeting),
  and the full strategy in
  [View Targeting](/guides/view-targeting/).
- Scaffold with the CLI instead: `ndigo new my-app --kind node` (see
  [The `ndigo` CLI](/guides/ndigo-cli/)).
- Working with an AI coding agent? Run `ndigo ai:init` to write the managed
  `AGENTS.md` block and skills — see
  [The Ndigo CLI § Agent context](/guides/ndigo-cli/#agent-context) and the
  [Agent Skills reference](/reference/skills/).
- Want agent-facing features? `ndigo add agent-surface --apply` wires an MCP
  server over your handlers, and
  `ndigo verify --capability agent-surface` proves the outcome — see
  [Capabilities](/guides/capabilities-for-authoring-agents/).
- Browse the [example apps](https://github.com/ndigo/ndigo/tree/main/apps) for
  working patterns (auth, ORM, caching, real-time, and more).
- Explore the [API reference](/reference/api/) for package-level documentation.

<Aside type="tip">
  Prefer a specific feature? Ndigo ships focused packages — `@ndigo/orm`,
  `@ndigo/auth-*`, `@ndigo/cache`, `@ndigo/jobs`, `@ndigo/socket`, and more.
  Add only what your app needs.
</Aside>
